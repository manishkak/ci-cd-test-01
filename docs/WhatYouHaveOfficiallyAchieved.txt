## 🔁 What happens on **every change**

When you edit `index.php`:
	1. You save code locally
	2. Git push to GitHub → GitHub repo is updated
	3. Run locally → you can see changes on localhost:8080 (Docker Desktop container running)
	4. Azure DevOps Pipeline (manual trigger)
	5. Checkout code
	6. Build new Docker image
	7. Push image to Docker Hub
	8. Azure Web App pulls latest Docker image
	9. Site updates at https://mkphpapp.azurewebsites.net/

👉 **No SSH**
👉 **No manual deploy**
👉 **No copying files**
👉 **No downtime**

That’s real CI/CD.

## 🧩 **What each part is responsible for (very important)**

### 🧑‍💻 **VS Code**

* Where **development** happens
* Nothing runs here in production
* You edit files like `index.php` locally and can test on **localhost:8080**

---

### 🐙 **GitHub**

* **Single source of truth**
* Any change must go here first
* Pipelines trust GitHub, not your laptop
* Commits pushed here trigger your CI/CD pipeline

---

### 🧪 **Azure DevOps Pipeline**

* The **brain** of the system

* Decides:
  * When to run
  * What to build
  * What to push
  * What to deploy
* Never runs app code directly — only builds & ships

---

### 🐳 **Docker**

* Freezes your app into a **portable container**
* Same container runs:
  * Locally (for testing)
  * In Azure DevOps pipeline
  * On Azure Web App
* Eliminates “works on my machine” problems
* Images are versioned and stored in **Docker Hub**

---

### 📦 **Docker Hub**

* **Image repository / warehouse**
* **Does not run containers**
* Stores **versions (tags)** of your images
* Source for deployments — Azure Web App pulls images from here

---

### ☁️ **Azure Web App (Linux + Docker)**

* **Runtime / host** for your container
* Always runs **the Docker image you tell it to - meaning on Manual trigger of Pipeline on Az DevOps page**
* **Stateless** — any changes inside container are ephemeral
* **Replaceable** — new deployments overwrite the running container
* **Scalable** — can increase instances if needed
* Automatically updates from Docker Hub when pipeline pushes a new image

2️⃣ CI Pipeline (Azure DevOps)
“Azure DevOps handles the CI/CD orchestration using a YAML pipeline.”

What the pipeline does:
Step-by-step inside the pipeline:
	1. Checkout code from GitHub
	2. Build a Docker image using a Dockerfile
	3. Tag the image (latest + commit-based tagging possible)
	4. Authenticate securely to Docker Hub
	5. Push the image to Docker Hub

💡 Why this matters:
	• Build environment is clean and consistent
	• No dependency on developer machines
	• Fully automated, repeatable process

3️⃣ Dockerization Strategy
“The PHP backend is fully Dockerized, which standardizes the runtime.”

Docker image contains:
	• PHP runtime
	• Apache
	• Application source code
	• All required PHP extensions

💡 Key benefit:
	• The same container runs:
		○ Locally
		○ in the pipeline
		○ in Azure production

This eliminates:
	• “Works on my machine”
	• Environment drift
	• Manual server configuration

4️⃣ Artifact Management (Docker Hub)
“Docker Hub is used as the container registry.”

	• The pipeline pushes the built image to Docker Hub
	• Docker Hub acts as:
		○ versioned artifact store
		○ deployment source for Azure

💡 Why this matters:
	• Clear separation:
		○ CI builds
		○ Registry stores
		○ Azure runs
	• Easy to roll back to a previous image tag

5️⃣ CD / Deployment (Azure Web App for Containers)
“Azure Web App for Containers pulls and runs the Docker image.”

How deployment works:
	• Azure Web App is configured with:
		○ Docker Hub registry
		○ Image name
		○ Tag (latest)
	• On new image push:
		○ Azure automatically pulls the updated image
		○ Restarts the container

💡 Key advantages:
	• No VM management
	• No SSH
	• No manual copying files
	• Azure handles:
		○ scaling
		○ health checks
		○ restarts

Flow:
